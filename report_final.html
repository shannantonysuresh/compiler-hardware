What this experiment stands in for

The patent disclosure's pipeline has five stages spanning five hardware targets (CPU/NVIDIA/AMD/TPU/FPGA). This machine has no discrete GPU and no C/LLVM toolchain installed, so this run substitutes two code-generation variants on one device: a naive scalar loop (interpreter-bound, standing in for unoptimized scalar codegen) versus a NumPy-vectorized loop (SIMD-bound, standing in for optimized/offloaded codegen). Everything downstream — characterization, cost formula, prediction, measurement, comparison — is the real mechanism from the disclosure, just applied to a CPU-only substitute pair instead of CPU-vs-GPU.

Cost model & prediction

For each loop, the model estimates total execution time on both variants and predicts a winner — mirroring the disclosure's Section 6 formula exactly:

T_total = max(T_compute, T_memory) + T_sync
T_compute = FLOPs / Peak_FLOPS   // vectorized path only
T_memory = Bytes / Bandwidth
T_sync   = branch_ratio × iterations × sync_latency  // vectorization penalty for divergent code
T_scalar = iterations × interpreter_overhead

Bug caught mid-run: the first version of this model used each benchmark's size parameter N directly for the scalar-overhead term. That's correct for the 1D loops, but wrong for stencil_2d (N = grid edge length, not iteration count = N²) and matmul (N = matrix dimension, not N³ iterations) — it silently predicted scalar as the winner for both. Fixed by tracking iteration count as an explicit field, separate from the problem-size parameter, in the characterization step.

Predicted vs. measured — the core result

BenchmarkArith. IntensityBranch %PredictedMeasuredMatch
vector_add0.0420%vectorvector✓ match

irregular_branchy_sum0.125100%scalarvector✗ miss
The one miss is the most informative result. The model predicted scalar would win irregular_branchy_sum because it charges the vectorized path a per-iteration sync/masking penalty proportional to branch ratio — mirroring the disclosure's claim that "high divergence indicates irregular execution unsuitable for SIMD." In reality, NumPy's boolean-mask vectorization (a[mask].sum()) still beat the scalar loop by 8×, because it evaluates the predicate as a vector op itself rather than branching per element. The disclosure's divergence penalty is real for GPU warp divergence, but the model's flat "branch_ratio × sync_latency" formula overcharges non-branching-hardware SIMD paths that use masking instead of control flow. This is exactly the kind of gap that only shows up by actually measuring — it wouldn't have been visible from the disclosure text alone.

Next steps

  • 01
    Fix the divergence-penalty termReplace the flat branch_ratio × sync_latency charge with a masking-aware model: distinguish "control-flow divergence" (costly on GPU warps) from "predicate masking" (cheap on CPU/GPU SIMD) as two different terms.
  • 02
    Add a real second deviceRent a cheap cloud GPU instance (e.g. AWS g4dn.xlarge, ~$0.50/hr) to run the same 5 benchmarks as actual CUDA kernels, to replace the "vectorized-CPU-as-GPU-proxy" stand-in with a genuine CPU-vs-GPU comparison.
  • 03
    Move characterization onto real IRInstall LLVM/Clang (not available on this machine today) and replace the hand-written analytical characterizer with an actual Polly/LLVM pass reading real IR, to remove the "we already know the loop structure" shortcut this prototype takes.
  • 04
    Grow the benchmark suitePull loops from Polybench/Rodinia instead of hand-written ones, to reduce the risk that 5 hand-picked benchmarks happen to flatter the model.
  • 05
    Re-run the accuracy metricOnce Steps 1–4 land, repeat this exact comparison methodology (Section 5) on real CPU-vs-GPU data and report the updated selection accuracy — that number is what belongs in the patent's TRL/validation section, which is currently blank.
